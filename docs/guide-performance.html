Performance Guide

How to get the most out of Axiom. Covers threading, GEMM tuning, op fusion, memory management, and profiling.

Threading

Axiom uses OpenMP for parallelism. The default thread count is the number of physical cores (not hyperthreads).

Manual Thread Control

// set to 4 threads
ax_set_num_threads(4);

// reset to default
ax_set_num_threads(0);

// query current count
int n = ax_get_num_threads();

Hybrid CPUs

On Intel 12th gen+ (Alder Lake, Raptor Lake) with P-cores and E-cores, the default OpenMP behavior can be catastrophic: slow E-cores hold up fast P-cores at barriers. Axiom provides:

int n = ax_autotune_threads();
printf("using %d fast cores\n", n);

This benchmarks each logical core with a pinned micro-workload, clusters them by speed, and restricts the thread pool to the fast cores. Total calibration time is under 200ms. Skipped if OMP_NUM_THREADS is set or AX_NO_AUTOTUNE=1.

Threading Best Practices

  • For small batch sizes (batch < 32), fewer threads can be faster because the per-thread overhead exceeds the compute savings.
  • The GEMM JC loop auto-shrinks when there are not enough column tiles to fill all threads.
  • OpenMP nesting is disabled: the conv2d batch loop and the GEMM JC loop use a guard (omp_in_parallel) to avoid nested parallelism.

Op Fusion

Fused operations reduce memory traffic by combining multiple ops into a single kernel pass. Use them whenever possible.

Fused Dense + ReLU

Instead of separate matmul and relu calls:

// slow: two passes over the output matrix
ax_tensor_t *h = ax_matmul_bias(x, w, b);
ax_tensor_t *a = ax_relu(h);

// fast: one pass, relu applied during gemm writeback
ax_tensor_t *a = ax_matmul_bias_relu(x, w, b);

In-Place Activations

// allocates a new tensor
ax_tensor_t *a = ax_relu(h);

// mutates h in place (when refcount is 1)
ax_relu_inplace(h);  // returns h, no allocation

In-place variants save one allocation and one full memory pass. They are safe when the storage refcount is 1 (no other tensors sharing the buffer). If refcount > 1, they silently fall back to the out-of-place variant.

Conv+BN+ReLU Fusion

// after building the model, fuse eligible triples
ax_sequential_fuse(net);

This replaces every contiguous Conv2D + BatchNorm + ReLU sequence in the sequential model with a single fused layer. The fused forward pass computes all three in one traversal of the output feature map.

GEMM Performance

Matrix multiplication dominates runtime for dense layers. Axiom's BLIS-style GEMM auto-tunes its tile sizes to your CPU's cache hierarchy at startup.

ISA Selection

The best SIMD backend is selected automatically at ax_compute_init() time:

When GEMM is Not the Bottleneck

For very small matrices (e.g., batch=1 inference with a small hidden layer), the pack overhead can dominate. In these cases:

  • Consider reducing the thread count to 1 (ax_set_num_threads(1))
  • The fused matmul_bias_relu eliminates post-gemm passes that would otherwise dominate

Memory Management

Arena Allocators

Axiom uses arena allocators for temporary buffers during forward and backward passes. Arenas allocate via bump pointer (extremely fast) and free in bulk. You do not need to manage these manually; they are handled by the autograd system.

  • Forward arena: temporaries that must survive through backward (batchnorm saved tensors). Reset by ax_graph_cleanup().
  • Backward arena: temporaries used only during backward. Reset after ax_backward() completes.

Conv2D Scratch Caching

Convolution layers cache their im2col buffers and GEMM scratch across batches. The ax_conv_scratch struct is lazily allocated on the first forward call and reused until the layer is destroyed. This avoids per-batch malloc/free for the (often large) im2col matrix.

Pack Buffer Caching

The GEMM backend caches packed B matrices (the weight matrix) keyed on the storage pointer and generation counter. When you run the same layer repeatedly (which is every training step), the packed B from the previous forward pass is reused if the weights have not changed. After an optimizer step, the generation counter increments and the cache invalidates.

Allocation Counting

Build with -DAX_COUNT_ALLOCS to track allocations:

uint64_t before = ax_get_alloc_count();
// ... run a training step ...
uint64_t after = ax_get_alloc_count();
printf("allocations: %lu\n", after - before);

CUDA Performance

When using the CUDA backend:

  • Keep data on the GPU. Set ax_set_default_device(AX_DEVICE_CUDA) at the start so tensors are created on the GPU. Avoid unnecessary host-device transfers.
  • Batch size matters more on GPU. Small batches underutilize the GPU. Use batch sizes of 128 or larger.
  • Fused kernels (add_relu, gemm_relu, bias_add) avoid extra kernel launches and memory round-trips.

Profiling

For detailed profiling, use your platform's tools:

  • Linux: perf stat and perf record for cycle-level profiling. perf stat -e cache-misses,cache-references to check cache behavior.
  • Valgrind: valgrind --tool=callgrind for call-graph profiling (slow but detailed).
  • CUDA: nsys profile for GPU timeline and kernel analysis.

Common things to look for:

  • L1/L2 cache miss rates during GEMM (should be very low if tiling is working)
  • Thread imbalance (one thread taking much longer than others at a barrier)
  • Unexpected allocations in the hot path (use AX_COUNT_ALLOCS)

Checklist

  1. Build with -DCMAKE_BUILD_TYPE=Release (enables -O3)
  2. Use ax_matmul_bias_relu() instead of separate matmul + add + relu
  3. Call ax_sequential_fuse() for CNN models
  4. Use in-place activations where possible
  5. Set thread count appropriately for your batch size
  6. On hybrid CPUs, call ax_autotune_threads() at startup
  7. For inference, use ax_no_grad() or build with AX_INFERENCE_ONLY
  8. Use batched inference (batch > 1) to amortize fixed overhead
