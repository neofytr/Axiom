Architecture Overview

How Axiom is structured internally, from the lowest backend layer up to the model API.

The Four-Layer Pipeline

Every computation in Axiom flows through a clean four-layer pipeline. Each layer has a well-defined responsibility and a clean boundary with its neighbors:

  User code
     |
  Layers       ax_dense_create, ax_layer_forward, ax_sequential_add
     |
  Ops          ax_add, ax_matmul, ax_relu  (autograd recording)
     |
  Compute      ax_compute_gemm, ax_compute_add  (dispatch + broadcast)
     |
  Backend      cpu_naive, cpu_opt, cuda  (raw kernel implementations)

Backend is the bottom layer. Each backend fills in an ax_backend_ops_t vtable with raw kernel implementations: element-wise ops, GEMM, reductions, activations. A backend is pure compute with no knowledge of autograd or broadcasting. The CPU naive backend is always available as a fallback. The optimized CPU backend adds SIMD GEMM, fused ops, and parallel reductions. The CUDA backend routes to cuBLAS and custom kernels.

Compute is the dispatch layer. It holds a pointer to the active backend's vtable and routes every call through it. This is where ISA dispatch happens: at startup, ax_compute_init() probes available backends and selects the best one. The compute layer also handles device routing, so ax_compute_gemm() on a CUDA tensor goes to the CUDA backend automatically.

Ops is the user-facing math layer. Functions like ax_add(), ax_matmul(), and ax_relu() live here. They handle output tensor allocation, shape validation, broadcasting, and (when grad tracking is enabled) recording the operation into the autograd computation graph. They call down into compute for the actual math.

Layers is the highest layer. A layer is a struct with a forward function pointer, parameter tensors, and train/eval mode. Layers compose into sequential models. ax_layer_forward() calls the layer's forward function, which calls ops, which call compute, which calls the backend. The chain is clean and each level adds exactly one concern.

Tensor Internals

The tensor is the fundamental data type. Understanding its internals is key to understanding everything else.

Structure

typedef struct ax_tensor {
    ax_storage_t *storage;         // shared data buffer
    int64_t shape[AX_MAX_DIMS];    // size of each dimension
    int64_t strides[AX_MAX_DIMS];  // element stride per dimension
    int ndim;                      // number of dimensions
    ax_dtype_t dtype;              // element type
    int64_t offset;                // element offset into storage
    bool requires_grad;
    struct ax_tensor *grad;
    void *grad_fn;                 // opaque pointer to grad function
} ax_tensor_t;

A tensor is a metadata wrapper around a storage buffer. The shape and strides arrays describe how to index into the flat data. Strides make zero-copy operations possible: a transpose just swaps two stride values without touching the data.

Storage and Refcounting

The actual data lives in ax_storage_t, a refcounted buffer:

typedef struct {
    void *data;            // raw data pointer (aligned)
    size_t size_bytes;
    atomic_int refcount;   // freed when it hits 0
    ax_device_t device;    // where this memory lives
    bool is_arena_temp;    // true if from a bump arena
    uint64_t generation;   // bumped on every write
} ax_storage_t;

Multiple tensors can share the same storage. When you call ax_tensor_view(), ax_tensor_reshape(), or ax_tensor_transpose(), you get a new tensor struct that points to the same storage with a different shape/strides/offset. The storage's refcount tracks how many tensors reference it. When the last tensor is destroyed, the storage is freed.

The Generation Counter

The generation field on storage is a subtle but important optimization. Caches (like the packed matrix buffers in the GEMM backend) key on the storage pointer. But optimizers update weights in-place without changing the pointer. The generation counter is bumped on every in-place write via ax_storage_touch(), so caches can detect stale entries and invalidate them. It starts at 1 and only goes up.

Views

Views are the reason tensors have strides and an offset. A view shares the same underlying data buffer but presents a different shape. This means:

  • ax_tensor_transpose(t, 0, 1) returns instantly by swapping strides. No data movement.
  • ax_tensor_reshape(t, new_shape, new_ndim) returns a view if the tensor is contiguous, or makes a copy if it is not.
  • ax_tensor_squeeze() and ax_tensor_unsqueeze() are pure metadata operations.

The tradeoff is that non-contiguous tensors require strided access patterns in compute kernels. Most backends check ax_tensor_is_contiguous() and fall back to a slower strided loop when needed.

Autograd Engine

Axiom uses reverse-mode automatic differentiation: it records a computation graph during the forward pass, then walks it backward to compute gradients.

The grad_fn Struct

struct ax_grad_fn {
    ax_backward_fn_t backward;     // the backward function
    ax_tensor_t *inputs[2];        // inputs to the forward op
    int n_inputs;
    ax_tensor_t *saved[4];         // tensors saved for backward
    bool saved_owned[4];           // whether grad_fn owns saved[i]
    int n_saved;
    double scalar_ctx;             // e.g. mul_scalar's scalar
    int int_ctx;                   // e.g. axis for sum
    void *ctx;                     // opaque extra context
    void (*ctx_cleanup)(void *);   // cleanup if backward never called
};

Every differentiable op in the ops layer creates a grad_fn and attaches it to the output tensor. The grad_fn stores:

  • A backward function pointer that computes input gradients given the output gradient
  • References to the input tensors (so gradients can be routed back)
  • Saved tensors that the backward function needs (e.g., ReLU saves its output to know which elements were zeroed)
  • Scalar/integer context for ops like ax_mul_scalar or ax_sum

Computation Graph and Backward Pass

The computation graph is implicit: it is the chain of grad_fn pointers attached to tensors. When you call ax_backward(loss), the engine:

  1. Performs a topological sort starting from the loss tensor, walking backward through grad_fn chains
  2. Initializes the loss gradient to 1.0
  3. Visits each node in reverse topological order, calling its backward function
  4. Each backward function computes gradients for its inputs and accumulates them (grad += computed_grad)

The topological sort ensures that when we visit a node, all its consumers have already contributed their gradients. This is the standard reverse-mode AD algorithm.

Memory Management in Autograd

Autograd is where memory management gets interesting. Three mechanisms keep allocations fast and leaks impossible:

Slab allocator for grad_fn. Instead of calling malloc for every grad_fn, Axiom uses a thread-local slab free-list. ax_grad_fn_create() pops from the free list (or allocates a slab of 64 grad_fn structs at once). ax_grad_fn_destroy() pushes back. This means creating a grad_fn is a pointer bump, not a syscall.

Backward arena. ax_backward_arena() returns a thread-local bump arena used for temporary buffers during the backward pass. Backward functions allocate from this arena instead of malloc. After ax_backward() completes, the arena is reset in bulk. This is much faster than individual frees and eliminates the risk of forgetting to free a temporary.

Forward arena. ax_forward_arena() provides similar arena allocation for forward-pass temporaries that need to outlive the forward pass and stay alive through backward. For example, batchnorm saves its normalized input (x_hat) and inverse standard deviation (inv_std) from the forward arena. These are only freed when ax_graph_cleanup() is called after the backward pass.

Graph cleanup. ax_graph_cleanup(loss) walks the computation graph from the loss tensor and destroys all intermediate (non-leaf) tensors. Leaf tensors (parameters, user-created tensors) are not touched. This is the companion call to ax_backward() and together they ensure a clean training loop with no leaks.

Lazy Zero Grad

A common optimization: instead of memset'ing every gradient tensor to zero before each step, Axiom uses a generation-counter approach. Fresh gradients skip the accumulate step and write directly. This avoids a full memory pass over every parameter at the start of each training step.

Compute Dispatch

The compute layer is a vtable-based dispatch mechanism. Every math operation goes through a function pointer in the ax_backend_ops_t struct.

The vtable Pattern

typedef struct {
    const char *name;
    ax_status_t (*add)(const ax_tensor_t *a, const ax_tensor_t *b, ax_tensor_t *out);
    ax_status_t (*gemm)(const ax_tensor_t *a, const ax_tensor_t *b, ax_tensor_t *out);
    ax_status_t (*gemm_nt)(...);   // optional: a @ b^T
    ax_status_t (*gemm_relu)(...);  // optional: relu(a @ b + bias)
    // ... 30+ more slots
} ax_backend_ops_t;

Optional operations (like fused GEMM+ReLU, AXPY, softmax) can be NULL. The dispatch layer checks for NULL and falls back to a decomposed path. For example, if gemm_relu is NULL, the caller falls back to gemm() + relu() as separate calls.

ISA Dispatch

On x86, ax_compute_init() probes CPUID for AVX-512 and AVX2 support. On ARM, it checks for NEON (which is always present on aarch64). The best available backend is selected automatically. You can also force a specific backend with ax_compute_set_backend().

Device Routing

Each backend can declare a device field. The CUDA backend sets device = AX_DEVICE_CUDA. When core code needs to allocate storage or transfer data for a CUDA tensor, it looks up the backend that owns AX_DEVICE_CUDA via ax_backend_for_device() and calls its memory hooks (storage_alloc, storage_free, memcpy_h2d, etc.).

GEMM: The Heart of Performance

Matrix multiplication dominates the runtime of neural network training and inference. Axiom implements BLIS-style tiled GEMM, the same algorithm used by production BLAS libraries.

The BLIS 5-Loop Structure

BLIS organizes GEMM into 5 nested loops that tile the computation to fit each level of the cache hierarchy:

// C [M x N] = A [M x K] @ B [K x N]
for jc = 0 .. N, step NC      // 5th loop: tiles columns of B for L3
  for pc = 0 .. K, step KC    // 4th loop: tiles K dimension for L2
    pack_b(B[pc:pc+KC, jc:jc+NC])  // pack B panel into contiguous buffer
    for ic = 0 .. M, step MC  // 3rd loop: tiles rows of A for L1
      pack_a(A[ic:ic+MC, pc:pc+KC])  // pack A panel
      for jr = 0 .. NC, step NR  // 2nd loop: micro-panel of B
        for ir = 0 .. MC, step MR  // 1st loop: micro-panel of A
          micro_kernel(A[ir:ir+MR, :], B[:, jr:jr+NR], C[ir:ir+MR, jr:jr+NR])

The key insight is that packing and tiling transform the random-stride access pattern of the original matrices into sequential scans that hit the cache hierarchy perfectly.

Micro-Kernel Sizes

The micro-kernel is the innermost loop: it computes an MR x NR block of C using an MR x K slice of A and a K x NR slice of B. The sizes are chosen to fill the register file:

ISAMR x NRRegisters UsedNotes
AVX-51214 x 32All 32 ZMM registers14 accumulators + broadcast + load
AVX26 x 1616 YMM registers6 accumulators + broadcast + load
NEON8 x 1232 NEON registers24 accumulators + 4 A loads + 3 B loads + 1 spare
Scalar4 x 4General-purpose regsFallback, no SIMD

Cache Tuning

The tile sizes NC, MC, KC are auto-tuned at startup to match the CPU's actual cache sizes. The goal is:

  • KC chosen so that the packed A micro-panel (MR x KC) fits in L1
  • MC chosen so that the packed A panel (MC x KC) fits in L2
  • NC chosen so that the packed B panel (KC x NC) fits in L3 (or a reasonable fraction of it)

This auto-tuning means the same binary performs well on different hardware without manual configuration.

Packing

Before the micro-kernel runs, slices of A and B are copied into contiguous, alignment-friendly buffers (pack_a and pack_b). This serves two purposes:

  • Eliminates stride arithmetic in the inner loop (the packed buffer is sequential)
  • Ensures proper alignment for SIMD loads (the pack buffers are 64-byte aligned)

Pack buffers are per-thread to avoid lock contention. The generation counter on storage lets the framework cache packed B buffers and invalidate them when the underlying weights change.

Threading

The JC loop (outermost, over columns of B) is parallelized with OpenMP. Each thread gets its own pack buffers. The thread count auto-shrinks when there are not enough JC tiles to fill all threads, avoiding the overhead of idle threads waiting at a barrier.

On hybrid CPUs (Intel 12th gen+ with P/E cores), ax_autotune_threads() benchmarks each logical core and restricts the thread pool to the fast cores, preventing slow E-cores from bottlenecking the barrier.

CUDA Backend

The CUDA backend provides GPU acceleration for all core operations.

cuBLAS Integration

GEMM is dispatched to cuBLAS via cublasSgemm. The backend maintains a cuBLAS handle and CUDA stream. All operations on the stream are serialized, matching Axiom's synchronous execution model.

Fused Kernels

Element-wise operations (add, mul, relu, sigmoid, tanh) are implemented as custom CUDA kernels. The fused variants (add_relu, gemm_relu, bias_add) run as single kernel launches, avoiding extra global memory round-trips.

Memory Model

CUDA tensors live in device memory. The ax_storage_t struct's device field tracks placement. Transfers between host and device use the backend's memcpy_h2d and memcpy_d2h hooks. The user-facing API is ax_tensor_to_cuda() and ax_tensor_to_cpu().

The global default device (ax_set_default_device(AX_DEVICE_CUDA)) controls where new tensors are allocated. Combined with ax_compute_set_backend(AX_BACKEND_CUDA), this routes the entire training loop to the GPU with no code changes.

Op Fusion

Axiom fuses several common operation patterns to reduce memory traffic:

MatMul + Bias + ReLU

ax_matmul_bias_relu() computes relu(A @ B + bias) in a single GEMM call. The ReLU is applied during the micro-kernel's writeback step, while the output is still in registers. This eliminates one full read+write pass over the output matrix.

Conv2D + BatchNorm + ReLU

ax_sequential_fuse() walks a sequential model and replaces every contiguous Conv2D-BatchNorm-ReLU triple with a single fused ax_conv_bn_relu_t layer. The fused forward pass computes all three operations in a single traversal of the output feature map.

Cross-Entropy Backward

The backward pass for cross-entropy loss with softmax computes softmax(pred) - target in one SIMD pass, instead of materializing the full softmax Jacobian matrix. For a batch of 256 with 10 classes, this avoids a 10x10 matrix per sample.

In-Place Activations

ax_relu_inplace(), ax_sigmoid_inplace(), and ax_tanh_inplace() mutate the input buffer directly when the storage refcount is 1 (no shared views). This halves the memory traffic for activation layers.

Layer System

Layers use C polymorphism: a base ax_layer_t struct with function pointers, and concrete layer types embed it as their first field.

struct ax_layer {
    ax_layer_ops_t ops;       // vtable: forward + destroy
    ax_layer_type_t type;
    bool training;
    ax_tensor_t *params[4];  // flat array, no heap
    int n_params;
    ax_tensor_t *buffers[4]; // non-trainable (running stats)
    int n_buffers;
};

The design is intentionally minimal for embedded targets: no heap-allocated strings, no dynamic arrays where avoidable, just function pointers and flat structs. Parameters are tracked in a fixed-size array (max 4 per layer, which covers weight+bias for dense and weight+bias+gamma+beta for batchnorm).

Error Handling

Axiom uses thread-safe error state. Every operation that can fail returns an ax_status_t enum. Detailed error messages are stored in thread-local storage and retrieved via ax_err_last_message(). An optional callback (ax_err_set_callback) can be installed for logging or custom error handling.
